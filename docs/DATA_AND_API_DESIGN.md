# 데이터·상태·API 설계 초안

기준일: 2026-10-13. 상태: 개념 계약. 최종 DB migration·OpenAPI 아님.
중요한 기술 제안: 버전이 있는 공통 콘텐츠와 개인 사용 기록을 분리한다.

## 데이터 책임

| 개념 | 저장할 정보와 책임 |
|---|---|
| 학습 공간 | 소유자, 원래 관심사, 현재 방향·목표 버전, 생성·보관 상태 |
| 방향 버전 | 사용자 목표·범위, 수준의 근거(사용자 진술/추정/시도), 경로, 템플릿 선택 |
| 콘텐츠 버전 | 블록 ID, 설명·예제·시각 데이터, 목적, 출처 버전, 유효·수정 상태 |
| 출처 버전 | URL/자료 ID, 소유·접근 범위, 조회 시점, 내용 digest, 인용 위치 |
| 생성 작업 | 요청 키·대상 버전·상태·시도·시간·모델/스키마 버전·비용·오류 코드 |
| 개인 활동 이벤트 | 인증에서 정한 소유자·기기·이벤트 ID·콘텐츠 버전·블록 노출/읽음 표시/실제 재생 구간/회상 유형·시점. 주의·이해의 보증 아님 |
| 이어보기 위치 | 기기/세션, 단원 버전·블록·재생 위치, 서버 반영 상태 |
| 회상 항목·시도 | 출처·단원 버전, 질문/답, 공개 조건, 시도 결과·판정 종류 |
| 복습 일정 | 대상 항목, 일정·산정 근거·수정 상태. 전역 숙련도 아님 |
| 이동 묶음 | 소유자, 단원 버전 목록, 파일 manifest·digest·크기·완료 상태 |
| 개념 연결 | 양 끝 ID·버전, 관계 종류·이유·제안 출처 |
| 공유 snapshot | 후속 단계. 공유한 자료 버전·허용 범위·개인 자료 포함 선택 |

위 표는 개념 설명이며 모든 것을 첫 단계에서 빈 모듈·테이블로 만들라는 지시가 아니다.

## 불변 조건

- 원문과 사용자 변경 의도를 AI 요약으로 대체하지 않는다.
- 콘텐츠를 바꾸면 새 버전을 만들고 과거 기록이 가리키는 버전을 유지한다.
- 생성·열람·재생·회상·적용은 다른 이벤트다.
- 모든 개인 데이터 조회·변경에는 인증된 소유자가 필요하다. ID를 아는 것만으로 접근할 수 없다.
- offline 이벤트는 소유자+eventId로 중복 적용하지 않는다.
- stale 방향·콘텐츠 변경은 충돌을 표시하거나 사용자가 고른 새 분기로 남긴다.
- 템플릿 재사용은 타인의 개인 상태를 복사하지 않는다.

## 상태 제안

생성 작업: QUEUED → RUNNING → READY | FAILED | CANCELLED.
오류 코드는 재시도 가능·근거 부족·한도 초과·결과 검증 실패를 구분한다.

콘텐츠: DRAFT → AVAILABLE → CORRECTION_NEEDED | SUPERSEDED.
DRAFT는 완료 자료로 사용자 학습 기록에 포함하지 않는다.

장치 이동 묶음: NOT_DOWNLOADED → DOWNLOADING → AVAILABLE_OFFLINE | PARTIAL | EVICTED | FAILED.
서버에 파일이 있다는 사실과 해당 기기에 오프라인으로 있다는 사실은 다르다.

## API 후보

| 동작 | 후보 API | 핵심 계약 |
|---|---|---|
| 관심사 시작 | POST /api/learning-spaces | 원문, 요청 키. 같은 키는 동일한 생성 결과 참조 |
| 개인 학습 목록 | GET /api/learning-spaces | 내 기록만 조회, 재개 요약 |
| 추천 방향 생성 | POST /api/learning-spaces/{id}/proposals | 목표 버전·작업 키, 작업 ID 반환 |
| 방향 선택/변경 | POST /api/learning-spaces/{id}/directions | 기대 버전·변경 범위, 새 방향 버전 |
| 다음 단위 생성 | POST /api/learning-spaces/{id}/units | 방향 버전·요청 키, 비용 한도, job ID |

| 활동 동기화 | POST /api/activity-events/batch | event ID별 처리 결과, 부분 성공 가능 |
| 이동 묶음 준비 | POST /api/offline-packs | 포함 버전·미디어, manifest |

API 이름은 변경 가능하다. 최초 구현 전에 요청/응답·오류·스키마와 HTTP 테스트를 하나의 행동 단위로 확정한다. 폴링은 첫 기본안이며 측정 없이 SSE·broker를 추가하지 않는다.

## 동시성과 중복

요청 키는 소유자·동작·정규 요청 내용에 묶는다. 동일 요청 재실행은 원래 생성 결과 또는 job 참조를 반환한다. 이후 바뀐 상태를 '처음 응답의 재현'으로 잘못 취급하지 않는다.

작업 생성·요청 키·설정한 사용량 예약은 한 트랜잭션으로 기록한다. 외부 호출 뒤 결과 적용은 현재 attempt/lease token, 작업 상태, 기대 방향/대상 버전의 compare-and-set을 함께 확인한다. lease 만료 뒤 옛 worker의 결과는 현재 상태에 적용하지 않는다. 외부 응답 유실·중복 호출의 과금 가능성과 결과의 중복 적용은 별개로 기록한다. 이미 방향이 바뀌었으면 결과를 현재 경로에 조용히 적용하지 않는다. 취소 이후 도착한 결과의 노출·비용 기록도 구분한다.

offline 활동은 로컬 outbox에 먼저 쓰고 foreground 재연결 때 재전송한다. batch는 ACCEPTED, DUPLICATE, RETRY_LATER, REJECTED, CONFLICT를 구분한다. 재시도 가능한 것만 자동 반복하고 영구 거절·충돌은 보존한 오류 상태에서 해결/폐기한다. 같은 eventId+다른 payload는 충돌이며, owner는 body가 아니라 인증에서 결정한다. 여러 기기의 시계·서버 반영 순서를 하나의 마지막 시간으로 덮어쓰지 않는다.

## offline 로그아웃과 소유권

로그아웃·계정 변경 시 미전송 outbox는 원래 owner에 묶어 보관하고 자동 삭제하지 않는다. 다른 owner의 화면·동기화에는 포함하지 않으며 원래 owner 재인증 후 이어 보낸다. 로그아웃 때 일반 콘텐츠 cache·메모리·재생 정보와 미전송 기록의 보관을 구분한다. 장치 저장소가 사용자가 직접 삭제되면 복구를 보증하지 않는다.

보관 정책의 구현안: 미전송 payload를 owner별로 암호화 보관하고 로그아웃 때 복원 key의 장치 cache·메모리를 제거한다. 원래 owner 인증 후에만 서버가 해당 owner의 복원 정보를 제공하는 방식이 추천이다. key를 잃지 않는 backup·rotation과 앱의 표준 암호화 사용을 S4의 독립 검토 대상으로 둔다. 프런트의 ownerId 필터만으로 접근 차단이 완료됐다고 쓰지 않는다. 처음부터 장치·브라우저 전체가 탈취된 경우의 완전 보호를 보증하지 않는다.

## 파일과 DB의 부분 실패

미디어를 임시 저장→파일 검증·지속 저장→DB 참조와 준비 상태 적용 순서로 처리하는 것이 추천이다. 필요한 파일과 DB 참조가 모두 준비되기 전 READY/AVAILABLE로 내보내지 않는다. 파일만 남으면 orphan으로 회수하고, 참조만 있으면 누락/재준비 상태로 표시한다. DB와 파일의 backup·restore는 같은 manifest 기준으로 정합성을 확인한다. 파일의 저장 성공을 데이터베이스 transaction의 원자성과 동일시하지 않는다.

offline 묶음은 재연결 때 수정 필요·삭제·버전 호환 상태도 확인한다. 틀린 옛 자료의 회상 기록은 새 버전 성공으로 옮기지 않는다.

## 삭제와 수정

자료·학습 공간 보관과 개인정보 삭제는 다른 동작이다. 삭제 시 활동·음성·이동 묶음·캐시를 어떤 범위로 제거할지 알려준다. offline 기기의 사본은 서버에서 즉시 지울 수 있다고 보증하지 않는다. 공유가 시작되기 전에 삭제·공유 철회 계약을 별도로 확정한다.


정상 종료와 로그아웃의 경계: 해당 owner로 로그인해 준비한 자료는 앱을 닫고 비행기 모드에서 다시 열어도 사용할 수 있어야 한다. 명시적 로그아웃·계정 변경은 모든 탭의 key·콘텐츠/재생 접근 상태를 제거한다. 암호화해 보관한 미전송 기록의 복원과 sync는 원 owner의 online 재인증 뒤 수행한다. 브라우저 저장소 자체가 삭제된 경우는 정상 종료와 다르다.
